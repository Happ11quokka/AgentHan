## 0. 에이전트에게 (먼저 읽기)

- 이 레포는 3파트로 나뉜다. 자기 파트 폴더만 고친다. 다른 파트 내부 코드를 import하지 않고 `src/agenthan/core/contracts.py`의 계약만 쓴다(§7). 파트를 묶는 코드는 `app/`과 `serve.py`에만 둔다.
- `core/contracts.py`를 고쳐야 하면 사람에게 알리고 멈춘다. 팀 규칙상 카톡 공지가 필요하다.
- 모델은 네이버 클라우드 것만 부른다(HyperCLOVA X, CLOVA Speech/Voice, CLOVA 임베딩, Papago). GPT·Whisper·Claude 같은 외부 모델 API를 코드에 넣지 않는다. 예외는 서버 안에서 도는 오픈 모델 하나다: 전화 말 끝 판정용 Smart Turn(ONNX, 외부 호출 없음, §2.2 Part C).
- CLOVA Studio 호출, 재시도, 모델 선택, RAG 기본값, LangGraph 예제는 `docs/sdk.md`를 기준으로 한다(§2.4). 이 파일은 gitignore 대상이라 레포에 없을 수 있다. 없으면 사람에게 카톡으로 받으라고 알린다.
- **데이터 원칙**: 실제 가게 데이터와 수집 코드는 `data/`·`private/`에만 둔다(gitignore + `.githooks/pre-commit`이 커밋을 막음). 절대 커밋·푸시하지 않는다. 레포·발표 자료·스크린샷·데모 영상 등 밖으로 나가는 것은 전부 `fixtures/` 더미 데이터로 통일한다. 수집 방법은 이 레포 문서에 쓰지 않는다(팀 내부 `private/README.md`).
- 테스트는 `fixtures/` 샘플과 `core/fakes.py`로 한다. DB 테스트는 `AGENTHAN_DB_URL`이 없으면 건너뛴다.
- **평가 기준과 언어 방침은 [`docs/eval-baseline.md`](eval-baseline.md)가 정본이다.** 이 PRD와 다르면 그 문서를 따른다. 요점: 비서 코어는 한국어만 다루고 사장님 언어는 앞단·뒷단에서 번역만 한다. 평가 데이터도 한국어(`ko`·`ko_simple`)만 쓴다.
- 지금 구현의 자세한 내용은 파트별 README가 정본이다: [`agent/README.md`](../src/agenthan/agent/README.md), [`rag/README.md`](../src/agenthan/rag/README.md), [`voice/README.md`](../src/agenthan/voice/README.md), [`app/README.md`](../src/agenthan/app/README.md), [`web/README.md`](../web/README.md), DB는 [`docs/db.md`](db.md), 비서 도구는 [`docs/tools.md`](tools.md).
- 용어는 상위 폴더의 `GLOSSARY.md`를 따른다. 사장님(사용자·점주라고 쓰지 않음), 손님(고객이라고 쓰지 않음), 오케스트레이터, 워커 에이전트, Tool Use, HITL.

## 1. 요약

비서가 하는 일을 두 가지로 봤다. 사장님의 가게 일을 돕는 것과 손님을 응대하는 것이다. 현장 인터뷰에서 외국인 사장님들은 네이버 기능이 있어도 몰라서 못 쓰고 있었고, 한국어가 되는 사람이 없을 때는 전화 주문을 받지 못했다. 그래서 가게 일은 사장님이 "메뉴 올려 줘", "요즘 리뷰 어때?"라고 말하면 스마트플레이스 기능을 찾아 입력까지 해 주고, 리뷰 정리처럼 반복되는 일은 비서가 루틴으로 제안한다. 손님 응대는 한국인 손님의 전화 주문을 AI가 한국어로 받아 사장님 언어로 넘긴다. **[확정]**

포지셔닝은 네이버 플랫폼 안에서 잘 동작하는 사장님의 personal agent다. 모든 기능을 일반 소상공인으로 넓힐 수 있지만, 확장성은 발표에서 언급만 한다.

### 2.2 파트별

**Part A 사장님 비서** (`agent/`, `tools/`, 도식 `03b`·`03`) **[구현]**

- 흐름(기본 `AGENT_MODE=planner`): 사장님 말 → 기능 후보(키워드 30% + 임베딩 70%, 상위 5개) → HCX-DASH-002 `select_feature`(후보 + 없음 + 되묻기) → HCX-007 계획 `{scope, steps, clarify}` → 단계마다 그 기능 도구만 붙여 실행(한 턴 모델 호출 10회 예산) → 쓰기는 미리보기 → 사장님 "네"에만 저장.
- 기능 카탈로그 `agent/place_features.json` 하나를 기능 매칭, 도구 연결, 평가 정답의 공통 원본으로 쓴다. 도구 목록은 [`docs/tools.md`](tools.md).
- 작업 원장(`task_ledger.py`): 여러 일을 한 번에 시키거나 중간에 다른 일을 끼워도 작업을 보류·재개한다. 값은 사장님이 이 대화에서 말한 것만 쓴다(`value_source.py`).
- 버튼(`/actions`)은 라우팅 없이 액션을 바로 실행하고, 답 아래 다음 액션 칩을 준다.
- 리뷰는 서브에이전트(`agent/review/`)에 위임: 분석·요약, 거친 표현 거르기, 미답글 답글 초안(답글 대기함), 정기 보고 루틴.
- 메뉴판 사진: HCX-005 비전으로 이름·가격 → 가게 지식과 대조(새 메뉴·가격 변경·변경 없음) → 사장님 승인 → 저장. 음식 사진: 메뉴 추측 + 배경 제거(흰 배경 정사각형).
- 가게 지식: 메뉴 확정은 이름·별칭·묶음으로만 찾고, 답글·톡톡 근거는 Part B 검색을 쓴다(PR #29).

**Part B 가게 지식** (`rag/`, `db/`, 도식 `04`) **[구현]**

- "메뉴 1개 = 문서 1개", 별칭 사전, 묶음(family) 구조.
- 검색 순서: 정확 일치(메뉴명·원어명·별칭) → 묶음 → 답할 수 없는 질문 → 의도 규칙 → 태그 → 종류 → 오타 허용 → BM25 + 벡터(RRF). 기준값은 `rag/rules.py` 한 곳.
- 품절은 거르지 않고 표시만, 근거가 없으면 빈 목록("모름"으로 답하거나 사장님께 넘김).
- 저장: 별칭·규칙·BM25는 Python, 벡터만 pgvector(HNSW, cosine). 메뉴·리뷰·가게 정보 조각을 모두 임베딩해서 `search_reviews()`·`search_store_info()`도 된다.
- 더미 가게 19곳 + 실제 1곳(`real`). 레포·발표는 더미, 실제 데이터는 서버 `data/`와 DB에만.
- 리랭커는 쓰지 않았다(규칙 + 하이브리드로 충분, 전화 지연 때문).

**Part C 전화 주문** (`voice/`, 도식 `05`·`06`·`phone-architecture`) **[구현]**

- 프레임워크(Pipecat·LiveKit) 없이 FastAPI + `grpc.aio` + `httpx`로 직접. 통화 세션(`call/`)은 포트(STT·TTS·시계·송신·`OrderSink`)로만 바깥과 만난다.
- STT: CLOVA Speech 스트리밍(gRPC, `semanticEpd`, 가게 메뉴 `keywordBoosting`). 4분 30초에 턴 사이 재연결.
- 말 끝 판정: 서버 무음 감지(RMS) → 끝말 규칙(이어짐·끝남·기다림) + Smart Turn v3.2 오디오 턴 모델(서버 안 ONNX) → 이어짐이면 2초 더 기다림. 첫 소리 전에 손님이 말을 이으면 답을 버리고 턴을 되감는다.
- 끼어들기: "말 끊기" 버튼 + 음성 끼어들기(에코 거르기).
- 대화: HCX는 슬롯 해석만, 대사는 상태 머신 템플릿. 복창·확인 전엔 주문 확정 안 함. 두 번째 되묻기엔 보기, 통화 전체 되묻기 5번이면 사장님께 넘김, 큰 수량(10개 이상)은 따로 확인.
- Part B 연결(11/21): 메뉴 이름을 못 알아들으면 검색 후보로 되묻고("꿀 들어간 거" → 메도빅?), 손님 질문 답에는 가까운 후기 3개를 근거로 넣는다.
- TTS: CLOVA Voice Premium `nara_call`, 150자 이하 문장, 동시 2개.
- 사장님 화면(`/owner`): 주문 카드·통화 자막, 메뉴명은 DB에서, 자유 문장만 Papago 번역(기본 러시아어). 모르는 질문은 질문 카드.
- 운영 방어: Origin·IP별 동시/시간당 상한, 하루 예산, 점검 모드, HCX 분당 한도와 규칙 대체, 로그 14일 보관, AI 고지 인사, `/healthz`, 배포 직후 스모크(`python -m agenthan.voice.smoke`).
- 가게 범용화: 가게 차이는 가게 JSON의 `phone` 묶음과 `MenuItem`으로만 낸다. 두 번째 더미 가게(쌀국수집)로 한 통화 끝까지 확인.

### 2.3 계약

`core/contracts.py`의 v1: `MenuItem`·`MenuHit`·`Review`·`StoreKnowledge`(B 제공), `Order`·`OrderLine`·`OrderSink`(C 생성). **[구현]**

- D2 결정: 계약 함수는 보통 함수(`def`)로 둔다. async 코드에서 부를 때 `asyncio.to_thread`로 감싼다. **[확정]**

## 3. 문제와 근거

| 관찰 | 근거 (인터뷰) | 우리 기능 |
|---|---|---|
| 네이버 기능은 많은데 사장님이 몰라서 못 쓴다 | 울란바토르: 네이버 리뷰 존재를 모름 · 믕밍: 플레이스 통계를 안 봄("할 게 너무 많아") | A 사장님 비서 |
| 한국어 메뉴 등록·설명이 어렵고 번역은 가게 맥락을 놓친다 | 냠냠: 뤄쓰펀 같은 낯선 메뉴, 어색한 메뉴 번역 · 5차: "취두부 쌀국수 → 그냥 쌀국수" | A 메뉴 등록 + B 가게 지식 |
| 부정 리뷰가 상처라 아예 안 본다 | 미미전병: "좋은 말은 하루 가는데 나쁜 말은 너무 오래 간다" | A 리뷰 요약·필터링 |
| 한국어 전화 주문을 못 받는다 | 미미전병: 어머니 혼자일 땐 전화 주문 불가 · 냠냠: AI 전화 주문에 긍정(인건비, 대기 줄) | C 전화 주문 |
| 이태원 식당 손님 70% 이상이 한국인인데 사장님은 한국어를 못 한다 | 10/29 이태원 인터뷰 | 전체 |
| 스마트콜/스마트 ARS는 버튼 5개·정해진 안내뿐, 주문·자유 대화 불가 | 6차 리서치 | C가 빈틈을 채움 |

## 4. 사용자

- 주 사용자는 외국인 사장님이다. 한국어 읽기·말하기가 서툴고, 모국어(러시아어·중국어·몽골어·영어 등)로 비서와 대화한다. 혼자 가게 일을 여럿 맡는다.
  - 구현 방침 **[확정]**: 비서 코어는 한국어만 다룬다. 모국어는 앞단(입력)·뒷단(출력) 경계에서 번역만 한다(`docs/eval-baseline.md` §0). 지금 번역 경계가 실제로 붙은 곳은 전화 사장님 카드(Papago)와 리뷰 번역이다. 비서 대화창의 모국어 입출력 번역은 아직 붙이지 않았다 **[미정]**.
- 손님은 한국인이고 전화로 한국어 주문을 한다(C).
- 초기 창업자 일반은 근거 인터뷰가 부족해 메인 타깃에서 뺐다. **[확정]**

## 5. 범위

### 하는 것 **[확정]**

1. A 사장님 비서(핵심): 웹 사장님 화면. 요청 → 플레이스 기능 매칭 → 도구로 실제 입력(더미 플레이스)까지. 리뷰 정기 보고 같은 루틴 제안. **[구현]**
2. B 가게 지식(기반): 외국인 가게 1곳의 메뉴·리뷰로 RAG를 만들고 A와 C가 같이 쓴다. **[구현]**
3. C AI 전화 주문(추가): 한국어만. 손님 전화에 답하고 턴을 조절하며 주문서를 사장님 화면에 사장님 언어로 넘긴다. **[구현]**

### 안 하는 것 **[확정]**

- 외부 지도(구글·카카오) 연동: 네이버 생태계 방향과 안 맞음
- 재고·발주: 노동 대체형이라 LLM 컨셉과 안 맞음
- 외국어 음성 전화: 손님이 한국인이라 당장 필요 없음
- 실제 전화번호(PSTN) 연결: 2주 안에 불가(`docs/research/03`). 실서비스 경로로만 설명
- 실제 사업자 인증이 필요한 플레이스 기능 직접 호출: 더미 API·더미 화면으로 대신하고 "실서비스에서는 네이버 기능에 연결"로 설명
- 컴퓨터 유즈(화면 클릭 자동화): MCP처럼 권한 있는 API 접근을 가정
- MCP 서버 시연, 봇 차단(Turnstile 등): 시간 부족으로 뺌

### 보류

- 현장 메뉴 설명(키오스크·QR 대신 설명형): 임팩트 있는 방식을 못 정함
- 손님 에이전트(네이버 Agent N)와 사장님 비서의 통신: 발표에서 확장성으로만 언급

## 6. 기능 요구사항

### 6.1 Part A · 사장님 비서 (`agent/`, `tools/`)

흐름: 사장님 입력(텍스트·사진·버튼) → 기능 매칭 → 계획 → 그 기능 도구 호출 → 결과를 사장님 말로 정리 → 되돌리기 어려운 동작은 미리보기 뒤 사장님 승인 후 실행(HITL).

구조: 오케스트레이터는 작업 원장과 요약만 든다. 리뷰처럼 긴 자연어 작업은 서브에이전트, 단순 조회·입력은 기능 도구. 한 단계에 그 기능 도구만 붙인다(계획 기능 최대 8개 + `ask_owner`).

| ID | 기능 | 사장님 한마디 예 | 완료 기준 | 상태 |
|---|---|---|---|---|
| A-0 | 기능 매칭·안내 | "손님한테 쿠폰 주고 싶어" | 플레이스 기능 목록에서 맞는 기능을 찾아 설명·실행한다. 목록에 없으면 도움말 검색이나 안내 | [구현] |
| A-1 | 메뉴 사진 → 메뉴 등록 | (메뉴판 사진) "이거 올려 줘" | 사진에서 메뉴명·가격을 읽고 기존 메뉴와 대조해 새 메뉴·가격 변경·변경 없음으로 보여 준다. 음식 사진은 메뉴를 추측하고 배경을 지운다. 사장님 승인 후 저장 | [구현] |
| A-2 | 최근 리뷰 요약·필터링 | "요즘 리뷰 어때?" | 상처 되는 표현은 거르고 칭찬·고칠 점을 정리한다. 원문은 펼쳐 볼 수 있다. 미답글 리뷰에 답글 초안을 미리 달아 두고(답글 대기함) 카드에서 올리기·고치기·건너뛰기 | [구현] |
| A-3 | 플레이스 통계 리포트 | "이번 주 손님 얼마나 왔어?" | 더미 통계(유입·시간대·요일·키워드)를 세 줄 카드(좋아진 점·살펴볼 점·할 일)로 요약하고 후속 질문("왜 줄었어?")에 답한다. 검색 노출 진단 포함 | [구현] |
| A-4 | 먼저 제안(루틴) | "매주 월요일에 리뷰 정리해 줘" / 비서 제안 | 리뷰 정기 보고 설정(주기·요일·시각·대상)을 미리보기 → 승인 뒤 저장. 답 아래 다음 액션 칩으로 이어서 할 일을 먼저 보여 준다 | [구현] (정해진 시각에 비서가 먼저 말을 거는 푸시는 없음) |
| A-5 | 그 밖의 플레이스 기능 | "금요일만 10시에 열어", "주문 3번 접수해" | 메뉴·업체 정보·영업시간·톡톡·주문·예약·대표키워드·쿠폰·새 오픈·매장결제(쓰기), 전화 기록·네이버페이·정산·POS·도움말(조회). [`docs/tools.md`](tools.md) | [구현] |

### 6.2 Part B · 가게 지식 (`rag/`, `db/`)

| ID | 요구사항 | 완료 기준 | 상태 |
|---|---|---|---|
| B-1 | 가게 1곳 데이터 준비 | 러시안 케이크 가게로 정함. 내부 개발은 실제 메뉴·설명·리뷰(`data/`, 커밋 금지), 판매·통계는 더미. **공개 자료는 전부 더미**(`fixtures/dummy_store/`) | [구현] |
| B-2 | 정제·마스킹 | 리뷰 작성자 마스킹, 메뉴 1개 = 문서 1개(`MenuItem`), 별칭·원어명·묶음·옵션 | [구현] |

> **데이터 원칙**: 개발은 내부 실제 데이터로 하고, 레포·발표·제출물은 `fixtures/` 더미 데이터로 통일한다. 더미는 실제 데이터와 같은 형식(`MenuItem`·`Review`)이라 설정 한 줄(`AGENTHAN_DATA_DIR`·`AGENTHAN_STORE_ID`)로 바꿔 끼운다.

### 6.3 Part C · AI 전화 주문 (`voice/`)

| ID | 요구사항 | 완료 기준 | 상태 |
|---|---|---|---|
| C-1 | 통화 채널 | 휴대폰 브라우저 통화 화면(`/phone`) → WebSocket → 서버. 심사위원이 폰으로 직접 주문해 볼 수 있다 | [구현] |
| C-2 | 음성 인식·합성 | CLOVA Speech 스트리밍, CLOVA Voice | [구현] |
| C-3 | 턴 관리 | 말 끝까지 기다리고 끝나면 빠르게 답한다. AI가 말하는 중 손님이 말하면 멈춘다(버튼·음성). 목표 말 끝 → 첫 소리 1.5초 | [구현] 스모크 P50 1.0~1.2초. 실기기(11/16)는 1.7~3.4초로 질문 답변 경로가 가장 느림 |

### 6.4 사장님 화면 (`web/`)

- `/`: 세 칸. 왼쪽 새 대화·자주 쓰는 일·최근 대화, 가운데 비서와 대화(사진 첨부·승인 카드·다음 액션 칩), 오른쪽 사이드카(내 가게·리뷰·손님 통계 탭). 비서가 저장하면 오른쪽이 바로 바뀐다. **[구현]**
- `/phone`: 손님 통화 화면. `/owner?key=…`: 사장님 전화 주문 카드. 왼쪽 메뉴 "전화 주문"에서 새 탭으로 연다. **[구현]**
- 디자인: 네이버 그린 `#03C75A`, Pretendard, 라이트 모드. 도구 이름·영문 코드는 화면에 안 보인다.
- 파일럿 매장: 새 대화는 가상 가게 하나(메뉴·리뷰·톡톡·주문·예약·통계가 같은 이야기)로 시작한다. `AGENTHAN_DATA_DIR=data/clean`이면 실제 매장 데이터로 띄운다(내부 확인용, 발표는 더미).

각 파트 폴더의 `README.md`에 담당·구현·실행법이 있다.

협업 규칙 **[확정]**: 비전공자도 있어서 편하게 간다.

- CI/CD 없음. 큰 작업은 PR로 합쳤다(#25·#27·#28·#29). 작은 문서 수정은 main에 바로 푸시해도 된다.
- 권장 두 가지: ① 자기 파트 폴더만 고친다 ② `core/`(계약)를 고칠 때는 카톡에 한 줄 공지.
- 푸시 전에 `git pull --rebase` 한 번.
- 비밀 키는 `.env`(커밋 금지). 형식은 `.env.example`. 서버 비밀은 `deploy/phone/.env`와 `private/`에만.
- 처음 한 번 `git config core.hooksPath .githooks`를 실행한다. 실제 데이터, 수집 코드, 네이버 지도 주소가 들어간 커밋을 이 훅이 막는다.
- 발표·캡처·데모 영상은 더미 데이터 모드로만 찍는다.
- 개인 에이전트 지침(`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.cursor/` 등)은 gitignore라 각자 스타일대로 쓴다. 공통으로 지킬 것은 이 PRD에만 적는다.
- 재배포: 서버에서 `git pull && ./deploy/phone/deploy.sh up`. 먼저 `/healthz`의 `active`(진행 중 통화)가 0인지 본다.

## 10. 평가와 E2E 기준

- 비서 평가의 구조·비율·회귀 게이트는 [`docs/eval-baseline.md`](eval-baseline.md)가 정본이다(시나리오 기준선 S1 하나를 게이트로, 한국어 케이스만). **[확정]**
- 비서 S1(92개 시나리오, 세션 최종 상태·안전 사건으로 채점): 기준선 95.3% → 튜닝 최종 99.6%(552회, 안전 위반·값 지어내기 0, `docs/s1-tuning-loh.md`). planner 루프 기본화 뒤 S1 97.7%, 다단계·단어 함정·범위 밖을 재는 S2 83.8%(PR #27). **[구현]**
- 비서 E2E: 사장님이 한마디 하면 function call부터 결과 정리까지 루프가 설계대로 끝까지 돈다. 미승인 쓰기 0. **[구현]**
- RAG: 골드셋·holdout으로 Recall@1·@3·MRR. 처음 보는 질문(holdout2) Recall@1 0.800. 근거 없는 질문은 빈 결과. **[구현]** `scripts/eval_rag.py`
- 전화: 대본 시나리오(`tests/voice/scenarios/`)로 상태·금지 규칙(확인 전 확정, 복창 없는 확인, 한 턴 두 질문 등)과 최종 `Order`를 본다. 배포 직후 스모크(대본 9개 + 통화 1건). 경로별 말 끝 → 첫 소리 P50·P90은 `voice.call.turn_summary`. **[구현]**
- 전화 지연: 목표 말 끝 → 첫 소리 1.5초. 스모크 P50 1.0~1.2초, 실기기는 질문 답변 경로에서 넘침. **[방향]**
