# AgentHan PRD: 외국인 사장님의 네이버 비서

> v0.2 · 2026-11-08 · 근거: 5차(11/2)·6차(11/6) 회의록, 10/19·10/28·10/29 인터뷰, `docs/research/`
> 이 문서는 사람과 코딩 에이전트가 같이 읽는다. 시각화 버전: [`docs/prd.html`](prd.html)
> 표기: **[확정]** 회의에서 정함 · **[방향]** 큰 방향만 정함, 개발하며 바꿀 수 있음 · **[미정]** 아직 정하지 않음

## 0. 에이전트에게 (먼저 읽기)

- 이 레포는 3파트로 나뉜다. 자기 파트 폴더만 고친다. 다른 파트 내부 코드를 import하지 않고 `src/agenthan/core/contracts.py`의 계약만 쓴다(§7).
- `core/contracts.py`를 고쳐야 하면 사람에게 알리고 멈춘다. 팀 규칙상 카톡 공지가 필요하다.
- 모델은 네이버 클라우드 것만 쓴다(HyperCLOVA X, CLOVA Speech/Voice, CLOVA 임베딩·리랭커, Papago). GPT·Whisper·Claude 같은 외부 모델 API를 코드에 넣지 않는다.
- CLOVA Studio 호출, 재시도, 모델 선택, RAG 기본값, LangGraph 예제는 `docs/sdk.md`를 기준으로 한다(§2.4). 같은 내용을 새로 만들지 말고 거기 적힌 계약을 따른다. 이 파일은 gitignore 대상이라 레포에 없을 수 있다. 없으면 사람에게 카톡으로 받으라고 알린다.
- **데이터 원칙**: 실제 가게 데이터와 수집 코드는 `data/`·`private/`에만 둔다(gitignore + `.githooks/pre-commit`이 커밋을 막음). 절대 커밋·푸시하지 않는다. 레포·발표 자료·스크린샷·데모 영상 등 밖으로 나가는 것은 전부 `fixtures/` 더미 데이터로 통일한다. 수집 방법은 이 레포 문서에 쓰지 않는다(팀 내부 `private/README.md`).
- 테스트는 `fixtures/` 샘플과 `core/fakes.py`로 한다.
- **평가 기준과 언어 방침은 [`docs/eval-baseline.md`](eval-baseline.md)가 정본이다.** 이 PRD와 다르면 그 문서를 따른다. 요점: 비서 코어는 한국어만 다루고 사장님 언어는 앞단·뒷단에서 번역만 한다. 평가 데이터도 한국어(`ko`·`ko_simple`)만 쓴다.
- 용어는 상위 폴더의 `GLOSSARY.md`를 따른다. 사장님(사용자·점주라고 쓰지 않음), 손님(고객이라고 쓰지 않음), 오케스트레이터, 워커 에이전트, Tool Use, HITL.

## 1. 요약

비서가 하는 일을 두 가지로 봤다. 사장님의 가게 일을 돕는 것과 손님을 응대하는 것이다. 현장 인터뷰에서 외국인 사장님들은 네이버 기능이 있어도 몰라서 못 쓰고 있었고, 한국어가 되는 사람이 없을 때는 전화 주문을 받지 못했다. 그래서 가게 일은 사장님이 모국어로 "메뉴 올려 줘", "요즘 리뷰 어때?"라고 말하면 스마트플레이스 기능을 찾아 입력까지 해 주고, 리뷰 정리처럼 반복되는 일은 비서가 먼저 루틴으로 제안한다. 손님 응대는 한국인 손님의 전화 주문을 AI가 한국어로 받아 사장님 언어로 넘긴다. **[확정]**

포지셔닝은 네이버 플랫폼 안에서 잘 동작하는 사장님의 personal agent다. 모든 기능을 일반 소상공인으로 넓힐 수 있지만, 확장성은 발표에서 언급만 한다.

## 2. 기술 스택 **[방향, 확정 아님]**

큰 방향만 정했고, 각 파트가 써 보고 바꿀 수 있다. 바꾸면 이 표를 고치고 카톡에 공지한다. 근거와 출처는 `docs/research/01~05`에 있다(2026-11-07 조사, 버전은 그날 PyPI·npm에서 확인). 도식은 `docs/diagrams/`.

### 2.2 파트별

**Part A 사장님 비서** (`docs/research/01`, 도식 `03b`·`03`)

- 흐름: 입력 → 규칙/버튼 → bge-m3로 기능 후보 5개 → HCX-DASH-002 `select_feature`(후보 + "없음") → 대표 기능이면 그 기능 도구 1~3개만 붙여 HCX-005 실행 → 아니면 설명·위치 안내.
- `features.json`(플레이스 기능 목록) 하나를 기능 매칭, 도구 연결, 골드셋 정답의 공통 원본으로 쓴다.
- 리뷰 요약·통계 보고서는 서브에이전트(질문 하나 → 마지막 답만). 오케스트레이터 상태에는 요약과 슬롯만.
- 먼저 제안(A-4): 정해진 시각에 리뷰·통계를 훑는 작업이 제안 카드를 만들고, 사장님이 받아들이면 루틴으로 저장한다. 대화 흐름과 같은 도구를 쓴다.
- 메뉴 사진: HCX-005 비전으로 읽기(네이티브 REST `dataUri`) → 텍스트 모델로 `MenuItem` JSON → 사장님 승인(`interrupt()`) → 저장. CLOVA OCR은 ko·ja·zh-TW만이라 키릴·베트남어 메뉴판엔 안 맞을 수 있다.
- 평가: pytest + `agentevals`(도구 호출 궤적 비교) + `pytest-recording`. LangSmith는 안 씀.

**Part B 가게 지식** (`docs/research/02`, 도식 `04`)

- 정확도는 "메뉴 1개 = 문서 1개", 별칭 사전, 하이브리드 검색에서 나온다. 우리 규모(문서 수천 개 미만)에선 벡터 DB 사이 성능 차이가 없어서 저장소는 편한 것을 고른다.
- 검색: ① 별칭 정확 일치 → ② 한국어 BM25(Kiwi 사용자 사전 + `bm25s`) + 벡터 → RRF 결합 → ③ 메타데이터 필터(품절·옵션).
- 저장소 **[방향, D1]**: 로컬은 sdk.md SQLite(또는 Chroma, 그때는 `cosine` 지정 필수)로 개발하고, 데모는 NCP Cloud DB for PostgreSQL + pgvector로 옮겨 "네이버 클라우드 위에서 동작"을 보여 주는 것을 추천한다. 11/08에 팀 NCP 계정 콘솔 접속은 확인했지만 서버와 Cloud DB는 아직 만들지 않았다. 서버를 만든 뒤 DB 접속을 확인하고, 확정은 B 담당이 11/10까지 정한다.
- 근거 고르기: Part A는 CLOVA 리랭커(인용 문서가 비면 "모름"), Part C는 지연 때문에 리랭커 없이 필드 값으로 바로 답.
- "네이버 연구실 RAG 기술" 주장은 공식 근거가 약하다. 발표에서는 "NAVER Cloud 공식 쿡북 구조(문단 나누기 → 임베딩 v2 → 벡터DB → 리랭커 → HCX) + CLOVA 인용형 RAG"로 말한다.
- 평가: 골드셋 CSV + id 기반 Recall@k·MRR 스크립트. 모호한 질문("쌀국수")도 골드셋에 넣는다.

**Part C 전화 주문** (`docs/research/03`·`05`, 도식 `05`·`06`)

- 프레임워크(Pipecat·LiveKit) 없이 FastAPI + `grpc.aio` + `httpx`로 직접. 모듈 5개: `ws_gateway`, `stt_clova`, `dialog`, `tts_clova`, `owner_hub`.
- STT: CLOVA Speech 스트리밍(gRPC, `nest.proto`는 API 문서 본문에 있음). 중간 결과 없음, EPD 확정만. 브라우저 VAD가 말 끝을 잡으면 `epFlag=true`로 확정을 앞당긴다. 연결 5분 제한 → 4분 30초에 턴 사이 재연결.
- 턴 판정(채널톡 구조 흉내): 브라우저 VAD(`@ricky0123/vad-web`, 멈춤 400~600ms) → 끝말 규칙 → HCX-DASH-002 3분류(끝남/이어짐/맞장구) → "이어짐"이면 최대 1.5초 더 기다림.
- 대화: HCX는 슬롯 추출과 분류만 하고, 대사는 상태 머신 템플릿이 맡는다. 복창·확인·정정을 상태 머신이 강제하고, 확인 전엔 주문 확정 이벤트를 안 보낸다. 늦게 온 결과는 `turn_id`로 버린다.
- TTS: CLOVA Voice, 화자 `nara_call`(상담원) 우선. 문장당 200자 제한 → 150자로 나눠 병렬 3개, 순서대로 재생.
- 사장님 화면: 메뉴명은 DB에서, 자유 문장만 Papago로 번역(몽골어처럼 Papago에 없는 언어는 HCX로). 모르는 질문은 질문 카드로 사장님께.
- 데모 폰은 안드로이드 크롬을 기본으로 한다(iOS 26.2+ Safari 에코 제거 버그 미해결).
- 평가(채널톡 축소판): AI 손님 + 텍스트 러너 + HCX 심판으로 시나리오 10개 × 5회, 음성 경로는 사람이 20통. 지표는 태스크 완료율, 오끊김률, 말 끝 → 첫 소리.

## 4. 사용자

- 주 사용자는 외국인 사장님이다. 한국어 읽기·말하기가 서툴고, 모국어(러시아어·중국어·몽골어·영어 등)로 비서와 대화한다. 혼자 가게 일을 여럿 맡는다.
  - 구현 방침 **[확정]**: 비서 코어는 한국어만 다룬다. 모국어는 앞단(입력)·뒷단(출력) 경계에서 번역만 한다. 한국어 코어 품질을 먼저 맞춘다(`docs/eval-baseline.md` §0).
- 손님은 한국인이고 전화로 한국어 주문을 한다(C).
- 초기 창업자 일반은 근거 인터뷰가 부족해 메인 타깃에서 뺐다. **[확정]**

## 5. 범위

### 하는 것 **[확정]**

1. A 사장님 비서(핵심): 챗봇 UI. 요청 → 플레이스 기능 매칭·제안 → 대표 기능 3개는 tool로 실제 입력까지. 데이터를 보고 리뷰 정리 같은 루틴을 비서가 먼저 제안하는 기능도 넣는다.
2. B 가게 지식(기반): 외국인 가게 1곳의 메뉴·리뷰로 사장님 RAG를 만든다. A와 C가 같이 쓴다.
3. C AI 전화 주문(추가): 한국어만. 손님 전화에 답하고 턴을 조절하며 주문서를 사장님 화면에 넘긴다.

### 안 하는 것 **[확정]**

- 외부 지도(구글·카카오) 연동: 네이버 생태계 방향과 안 맞음
- 재고·발주: 노동 대체형이라 LLM 컨셉과 안 맞음
- 외국어 음성 전화: 손님이 한국인이라 당장 필요 없음
- 실제 전화번호(PSTN) 연결: 2주 안에 불가(`docs/research/03`, 상위 `.scratch/.../17`). 실서비스 경로로만 설명
- 실제 사업자 인증이 필요한 플레이스 기능 직접 호출: 더미 API·더미 화면으로 대신하고 "실서비스에서는 네이버 기능에 연결"로 설명
- 컴퓨터 유즈(화면 클릭 자동화): MCP처럼 권한 있는 API 접근을 가정

### 보류

- 현장 메뉴 설명(키오스크·QR 대신 설명형): 임팩트 있는 방식을 못 정함
- 손님 에이전트(네이버 Agent N)와 사장님 비서의 통신: 발표에서 확장성으로만 언급

## 6. 기능 요구사항

### 6.1 Part A · 사장님 비서 (`agent/`, `tools/`)

흐름: 사장님 입력(모국어 텍스트·사진) → 오케스트레이터가 의도 파악 → 플레이스 기능 매칭 → (대표 기능이면) tool 호출 → 결과를 사장님 언어로 정리 → 되돌리기 어려운 동작은 사장님 승인 후 실행(HITL).

구조 **[방향]**: 오케스트레이터는 정제된 맥락만 든다. 리뷰 요약·보고서처럼 긴 자연어 작업은 서브에이전트(워커), 단순 조회·입력은 function call. 도구를 한꺼번에 다 붙이지 않는다(컨텍스트 초과).

| ID | 기능 | 사장님 한마디 예 | 완료 기준 | 상태 |
|---|---|---|---|---|
| A-0 | 기능 매칭·안내 | "손님한테 쿠폰 주고 싶어" | 전체 플레이스 기능 목록에서 맞는 기능을 찾아 사장님 언어로 설명하고 위치를 알려 준다 | [확정] |
| A-1 | 메뉴 사진 → 메뉴 등록 | (메뉴판 사진) "이거 올려 줘" | 사진에서 메뉴명·가격을 읽고, 한국어 메뉴명·설명을 가게 맥락에 맞게 만들어 오른쪽 더미 플레이스 메뉴 화면에 채운다. 사장님 승인 후 저장 | [확정] |
| A-2 | 최근 리뷰 요약·필터링 | "요즘 리뷰 어때?" | 리뷰를 가져와 상처 되는 표현은 걸러 내고 칭찬·고칠 점을 사장님 언어로 정리한다. 원문은 펼쳐 볼 수 있다 | [확정] |
| A-3 | 플레이스 통계 리포트 | "이번 주 손님 얼마나 왔어?" | 더미 통계(유입 경로·시간대·요일별)를 조회해 사장님 언어로 요약하고 한 가지 행동을 제안한다 | [확정] |
| A-4 | 먼저 제안(루틴 등) | — (비서가 먼저 말을 건다) | 리뷰·통계 데이터를 보고 반복할 만한 일을 비서가 먼저 제안한다. 예: "새 리뷰가 쌓였어요. 매일 저녁 요약해 드릴까요?" 사장님이 받아들이면 루틴으로 등록한다. 주기는 실제 리뷰 빈도를 보고 정한다(대회용 주 10건 가정) | [방향] |

### 6.2 Part B · 가게 지식 (`rag/`)

B는 가장 먼저 끝나야 한다. 심사위원이 우리 DB 안에서만 테스트하므로 검색이 틀리면 점수가 바로 깎인다. **[확정]**

| ID | 요구사항 | 완료 기준 | 상태 |
|---|---|---|---|
| B-1 | 가게 1곳 데이터 준비 | 메뉴·리뷰가 많은 외국인 가게(후보: 러시안 케이크 가게). 내부 개발은 실제 메뉴·설명·리뷰(`data/`, 커밋 금지), 판매·통계는 더미. **공개 자료는 전부 더미** | 가게 [미정] |
| B-2 | 정제·마스킹 | 리뷰 작성자 마스킹, 메뉴 1개 = 문서 1개(`MenuItem`), 별칭(`aliases`)·원어명(`name_native`)·옵션 가능 여부 | [방향] |
| B-3 | 사장님 RAG | `StoreKnowledge` 구현. "쌀국수"가 여러 메뉴 중 무엇인지, "고수 빼 주세요"가 되는지, 근거 없으면 빈 결과 | [확정] |
| B-4 | 플레이스 기능 RAG | 스마트플레이스 기능 목록(Part A 리스트업 결과)을 검색해 사장님 요청과 매칭. 규칙 기반에 가깝게 | [방향] |
| B-5 | 질문 시나리오·골드셋 | 사장님·손님이 실제로 어떻게 물을지 시나리오를 먼저 설계. 질문-정답 메뉴 쌍으로 골드셋 | [확정] |

> **데이터 원칙**: 개발은 내부 실제 데이터로 하고, 레포·발표·제출물은 `fixtures/` 더미 데이터로 통일한다. 더미는 실제 데이터와 같은 형식(`MenuItem`·`Review`)이라 설정 한 줄로 바꿔 끼운다.

기술보다 "사장님이 어떻게 물을까" 시나리오를 먼저 설계한다. 다국어 질의는 메뉴 용어집(`name_ko`·`name_native`·`aliases`)으로 한국어로 바꿔 한국어 인덱스 하나에서 찾는다(상위 폴더 `리뷰답변-다국어설계-리서치.html` D2).

### 6.3 Part C · AI 전화 주문 (`voice/`)

| ID | 요구사항 | 완료 기준 | 상태 |
|---|---|---|---|
| C-1 | 통화 채널 | 휴대폰 브라우저 통화 화면 → WebSocket → 서버. 심사위원이 폰으로 직접 주문해 볼 수 있다 | [확정] |
| C-2 | 음성 인식·합성 | CLOVA Speech(STT) 스트리밍, CLOVA Voice(TTS) | [확정] |
| C-3 | 턴 관리 | 손님 말이 끝날 때까지 기다리고, 끝나면 빠르게 답한다. AI가 말하는 중 손님이 말하면 멈춘다(barge-in). 목표: 말 끝 → 첫 소리 1.5초 이내 | [방향] |
| C-4 | 주문 대화 | 메뉴·옵션·수량·픽업 시간을 묻고 `StoreKnowledge`로 확인. 마지막에 복창·확인 | [확정] |
| C-5 | 단순 안내 분리 | 주차·영업시간 같은 단순 정보는 스마트 ARS 영역으로 두고, 나머지를 AI가 처리 | [방향] |
| C-6 | 주문서 전달 | `Order`를 `OrderSink`로 넘기고, 사장님 화면에 사장님 언어로 표시. 모르면 사장님 연결/문자로 넘김 | [방향] |

벤치마크는 채널톡 보이스 ALF(2026-10-21 정식 출시)다. 턴 감지와 복창 설계를 참고한다(`docs/research/05-channeltalk-voice-benchmark.md`).

### 6.4 사장님 화면 (`web/`)

- 왼쪽 대화창 + 오른쪽 더미 스마트플레이스 화면. 에이전트가 오른쪽 폼을 채우는 모습을 보여 준다(Claude 데스크톱 앱처럼). **[확정]**
- 전화 데모 화면(손님용 통화 화면, 사장님용 주문서 화면).
- 기능을 먼저 돌아가게 만들고 UI는 마지막 이틀에 다듬는다. 디자인은 그림 잘 그리는 팀원이 도울 수 있으면 반영. **[확정]**

**따로 만들고 잘 합치는 규칙 [확정]**

1. 계약 먼저: 파트 사이에 오가는 것은 `core/contracts.py`의 타입과 Protocol뿐이다. 지금 정의된 것: `MenuItem`·`MenuHit`·`Review`·`StoreKnowledge`(B가 제공), `Order`·`OrderLine`·`OrderSink`(C가 생성). 초안 v0이며 첫 주에 함께 확정한다.
2. 가짜로 먼저 개발: A와 C는 B를 기다리지 않는다. `core.fakes.FakeStoreKnowledge.from_fixture()`로 개발하고, 합칠 때 `app/`에서 진짜 구현으로 바꿔 끼운다.
3. 계약 테스트: `tests/test_contracts.py`가 진짜 구현으로도 통과하면 합칠 수 있다. B는 구현을 만들면 `IMPLEMENTATIONS`에 추가한다.
4. 경계: 파트끼리 서로의 내부(`agenthan.rag.*` 등)를 import하지 않는다. 통합 코드는 `app/`에만 둔다.

각 파트 폴더의 `README.md`에 담당·할 일·import 규칙이 있다.

협업 규칙 **[확정]**: 비전공자도 있어서 편하게 간다.

- CI/CD 없음. PR 필수 아님. main에 바로 푸시해도 된다.
- 권장 두 가지: ① 자기 파트 폴더만 고친다 ② `core/`(계약)를 고칠 때는 카톡에 한 줄 공지.
- 푸시 전에 `git pull --rebase` 한 번.
- 비밀 키는 `.env`(커밋 금지). 형식은 `.env.example`.
- 처음 한 번 `git config core.hooksPath .githooks`를 실행한다. 실제 데이터, 수집 코드, 네이버 지도 주소가 들어간 커밋을 이 훅이 막는다.
- 발표·캡처·데모 영상은 더미 데이터 모드로만 찍는다.
- 개인 에이전트 지침(`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.cursor/` 등)은 gitignore라 각자 스타일대로 쓴다. 공통으로 지킬 것은 이 PRD에만 적는다.

## 10. 평가와 E2E 기준

- 비서 평가의 구조·비율·회귀 게이트는 [`docs/eval-baseline.md`](eval-baseline.md)가 정본이다(시나리오 기준선 S1 하나를 게이트로, 한국어 케이스만). 아래 "도구 호출 벤치마크" 항목은 S1과 그 문서의 L2 진단으로 대체한다. **[확정]**
- 비서 E2E: 사장님이 한마디 하면 function call부터 결과 정리까지 루프가 설계대로 끝까지 돈다. **[확정]**
- 전화 E2E: 손님 전화에 답을 잘 하고 턴 조절이 된다. **[확정]**
- 도구 호출 벤치마크: 가게 하나를 정해 기능을 잘게 쪼갠 자연어 명령 시나리오(목표 100개)를 만들고, 올바른 도구를 부르는지 잰다. 정답 데이터가 없는 주제라서, 정확도 수치보다 설계대로 동작하는지를 본다. **[확정]**
- RAG: 골드셋으로 메뉴 검색 정확도를 잰다. 근거 없는 질문에는 "모른다"고 답하는지 확인한다. **[방향]**
- 전화 지연: 손님 말 끝 → 첫 소리 1.5초 이내를 목표로 잰다. **[방향]**

| HCX 도구 호출·비전 정확도 공개 수치 없음 | A 데모 실패 | 11/10~11에 기능 매칭 골드셋(30개라도)부터 돌려 모델·구조 결정. 도구는 고른 기능 것만 1~3개 붙임 |
| CLOVA 공통 클라이언트를 직접 만들어야 함 | 첫 주 A·C 개발 지연 | sdk.md 3장 REST 계약·재시도 코드를 그대로 옮김. 첫날 Chat·도구 호출·이미지·스트리밍 스모크 테스트 |
| 사장님 모국어(몽골어·러시아어 등) 이해도 미확인. Papago는 13개 언어만이라 몽골어는 안 됨 | 모국어 대화 품질 | 코어는 한국어만 다루고 모국어는 앞단·뒷단 번역으로 처리(`docs/eval-baseline.md` §0). Papago 우선, 몽골어처럼 없는 언어는 HCX 번역. 번역 품질은 코어 평가와 따로 잰다 |
| 휴대폰 마이크는 HTTPS에서만 동작 | 전화 데모 불가 | 11/13까지 HTTPS 배포, 안드로이드·아이폰 실기 확인 |
| iOS 26.2+ Safari 재생음 지직거림(WebKit 버그 미해결) | 아이폰 체험 품질 | 데모 폰은 안드로이드 크롬 |
| CLOVA Speech·HCX·Voice 지연 공식 수치 없음 | 1.5초 목표 미달 | 11/10까지 단계별 실측, "네," 선응답·템플릿 응답, 안 되면 누르고 말하기 모드 |
| CLOVA Voice 기본료(만들면 바로 부과)·Object Storage 버킷 선행 | 준비 지연·비용 | 리소스는 한 사람이 만들고 크레딧 확인 후 생성 |
| 사장님 RAG가 늦어짐 | A·C 둘 다 막힘 | 가짜 구현으로 병행 개발, B를 최우선 |
| 실제 사장님 섭외 불가 | 데이터 현실성 | 내부는 외국인 가게 1곳 실제 메뉴·리뷰, 공개는 더미 + 더미 통계 |
| 실제 전화번호 연결 불가 | 전화 데모 현실감 | 휴대폰 브라우저 통화 화면 + 실서비스 경로 설명 |
| 사업자 인증 필요한 플레이스 기능 | 실제 호출 불가 | 더미 API·화면, "네이버 기능에 연결 가능" 설명 |
| 크레딧이 서브 계정에 안 보임 | 비용 | 조직 주 계정 크레딧 여부를 운영 측에 확인. 그전엔 리소스를 만들지 않음 |
| main 자유 푸시 충돌 | 작업 유실 | 폴더 소유, `pull --rebase`, 작은 커밋 |
