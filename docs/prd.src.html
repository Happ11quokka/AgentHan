AgentHan · 외국인 사장님의 네이버 비서

비서가 하는 일을 두 가지로 봤다. 사장님의 가게 일을 돕는 것과 손님을 응대하는 것이다. 현장 인터뷰에서 외국인 사장님들은 네이버 기능이 있어도 몰라서 못 쓰고 있었고, 한국어가 되는 사람이 없을 때는 전화 주문을 받지 못했다. 그래서 가게 일은 사장님이 모국어로 한마디 하면 스마트플레이스 기능을 찾아 입력까지 해 주고, 리뷰 정리 같은 반복 일은 비서가 먼저 루틴으로 제안한다. 손님 응대는 한국인 손님의 전화 주문을 AI가 한국어로 받아 사장님 언어로 넘긴다.

  • 시연할 기능 3개: 메뉴 사진 → 메뉴 등록, 최근 리뷰 요약, 플레이스 통계 리포트. 되돌리기 어려운 저장은 사장님 승인 뒤에만 한다.
  • 기술 방향: HyperCLOVA X(005·DASH-002) + LangGraph, CLOVA 임베딩 + 하이브리드 검색, CLOVA Speech·Voice. 모델은 전부 네이버 클라우드 것을 쓰고, FastAPI + React를 NCP Server 1대에 올린다.
  • 데이터 원칙: 개발은 내부 실제 데이터로 하고, 레포·발표·제출물은 전부 더미 데이터로 통일한다. 실제 데이터는 절대 커밋하지 않는다.
  • 정할 것: 데모 저장소(D1), 계약 함수 동기/비동기(D2)를 11/10까지.

Part B · 가게 지식

심사위원은 우리 DB 안에서만 테스트한다. 검색이 틀리면 점수가 바로 깎인다. 정확도는 메뉴 1개 = 문서 1개, 별칭 사전, 하이브리드 검색에서 나온다. 우리 규모(문서 수천 개 미만)에서는 벡터 DB 사이 성능 차이가 없어서 저장소는 편한 것을 고른다.

데이터 원칙 · 팀 결정
  • 실제 가게 데이터와 관련 코드는 data/·private/에만 둔다. gitignore와 .githooks/pre-commit이 커밋을 막는다. 절대 커밋·푸시하지 않는다.
  • 레포·발표 자료·스크린샷·데모 영상·제출물은 전부 fixtures/ 더미 데이터로 통일한다.
  • 더미는 실제 데이터와 같은 형식(MenuItem·Review)이라, 설정 한 줄로 바꿔 끼운다.

Part C · AI 전화 주문

한국어만 지원한다. 실제 전화번호는 2주 안에 붙일 수 없어서 휴대폰 브라우저 통화 화면에서 WebSocket으로 서버에 붙여 시연한다. 심사위원이 자기 폰으로 직접 주문해 볼 수 있다. 벤치마크는 채널톡 보이스 ALF다.

정할 것

[D1]데모 저장소 (11/10, B 담당 정민서)

아직 확정이 아니라 추천이다. 11/08에 팀 NCP 계정(한양대학교 조직의 서브 계정)으로 콘솔에 들어가는 것까지 확인했다. 서버와 Cloud DB는 아직 하나도 만들지 않아서, 서버에서 DB로 붙는지는 서버를 만든 뒤 확인한다.

로컬에서는 SQLite/Chroma로 개발하고, 데모 전에 NCP Cloud DB for PostgreSQL + pgvector로 옮긴다. 검색 정확도는 저장소와 상관없고, 발표에서 "네이버 클라우드 위에서 동작"을 보여 줄 수 있다.

[D2]계약 함수를 동기로 둘지 비동기로 바꿀지 (11/10)

서버 하나가 사장님 채팅과 손님 전화를 동시에 받는다. search_menu()처럼 HCX나 DB에 다녀오는 함수를 그냥 부르면, 답을 기다리는 동안 다른 사람의 요청까지 멈출 수 있다. 이걸 막는 방법이 두 가지다. 계약 함수 자체를 async def로 바꾸거나, 보통 함수로 두고 부르는 쪽에서 별도 스레드로 돌리는 것이다.

계약은 지금처럼 보통 함수(def)로 둔다. async 코드(app/의 핸들러, voice/ 안의 전화 처리)에서 부를 때만 asyncio.to_thread()로 감싼다. 파트 담당자는 async를 몰라도 되고, 시연 규모(동시 접속 몇 명)에서는 이걸로 충분하다.
