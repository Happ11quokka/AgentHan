# 채널톡 보이스 ALF 벤치마크 — 설계 근거와 우리가 가져올 것

> 선행 조사 [17-ai-phone-order-on-ncp.md](../../../.scratch/ai-biseo-ideation/research/17-ai-phone-order-on-ncp.md)의 Q4(채널톡 출시 기사, 빠른 배포·IVR 두 방식, v2 규칙·지식)는 다시 쓰지 않았다. 이 문서는 그 뒤에 찾은 **채널톡 기술 블로그·도움말·채용 공고**와 관련 논문을 다룬다.

## 요약

1. 채널톡 턴 감지(TD)는 **음성만 보고 "지금 답할지 / 더 기다릴지"를 고르는 분류 모델**이다. Gemma4-2B의 생성 헤드를 분류 헤드로 바꿨다. VAD가 멈춤을 잡으면 STT와 **병렬로** 돌린다. 중앙값 116ms, 오끊김 5% 기준 평균 대기 0.58초다. [공식] 기술 블로그 2026-09-10
2. "87% / 1.5초"는 사내 카페 전화 2주(2026-08-24~09-07) 판단 8,210건 중 **'기다리기' 2,011건의 87%(1,750건)가 1.5초 안에 말을 이었다**는 운영 관측값이다. 도입 전후 개선율이 아니다. [공식]
3. 아웃바운드 엔진은 **LLM에게 대사를 맡기지 않고 분기 분류만** 맡긴다. 텍스트 기반 "의미 VAD(SVAD)"로 답변이 끝났는지 판단한다. 정확도가 중요한 값은 **읽어 주고 확인받고, 정정하면 다시 확인**한다. [공식] 2026-10-23
4. 품질 검증은 **AI 손님 + 텍스트 러너 + AI 심판(전사와 실행 로그 비교)** 루프다. 8개 체크를 모두 통과해야 PASS다. 직접 테스트 전화가 Task당 약 50통에서 5통으로 줄었다. barge-in과 STT 정확도는 아직 사람이 확인한다. [공식] 2026-10-29
5. 우리는 자체 오디오 TD 모델을 학습할 수 없다. 대신 **VAD 무음 + 규칙 + HCX 완결성 판정(끝남/이어짐/맞장구 3분류) + 최대 1.5초 추가 대기**로 같은 구조를 흉내 낸다. 평가는 채널톡과 같은 두 지표(오끊김률, 평균 대기)로 한다. [추론]

## 2. 턴 감지(TD) 설계 — 기술 블로그 2026-09-10

| 항목 | 내용 | 등급 |
|---|---|---|
| 문제 정의 | 전화에는 전송 버튼이 없다. 멈출 때마다 "지금 답할지, 더 기다릴지"를 정해야 한다. 예: "사용 기간이 2년이 안 돼서…"는 답해도 된다. "기기 번호요? 잠시만요."와 "핸드폰 번호 공 일 공에…"는 기다려야 한다. | [공식] |
| 무음 임계값의 한계 | 짧게 잡으면 말을 끊고, 길게 잡으면 침묵이 남는다. 같은 침묵도 문맥과 억양에 따라 뜻이 다르다. | [공식] |
| 역할 분담 | VAD는 "음성이 멈춘 시점"만 찾는다. 답할지는 TD가 정한다. 따로 **최대 대기 시간**을 둬서 너무 오래 기다리지 않게 한다(값은 비공개). | [공식] |
| 파이프라인 | 멈춤 감지(VAD) 직후 TD를 **STT와 병렬로** 실행한다. "답하기"면 지금까지 전사를 LLM에 넘기고 TTS로 말한다. "기다리기"면 다음 음성을 계속 받는다. | [공식] |
| 입력 | **오디오만** 쓴다. 전사 텍스트를 안 쓰므로 STT 지연과 오인식의 영향을 받지 않고 억양·머뭇거림을 직접 본다. 텍스트 모델과의 비교 실험은 글에 없다. | [공식] |
| 모델 | Google Gemma4-2B(오디오 인코더 + LLM). 텍스트 생성 헤드를 **분류 헤드**로 바꿔 선택지별 점수만 낸다. 경량화 내용은 없다. | [공식] |
| 정답 라벨 | 실제 상담 발화 약 1,000개를 사람이 듣고 907개를 남겼다. **말이 끝남 416 / 아직 말하는 중 431 / 맞장구 60**. 맞장구("네네", "아 그렇군요")를 따로 둔 이유는 답을 요구하는 말인지 단순 반응인지 가르기 위해서다. | [공식] |
| 자동 라벨러 | 학습 후보 약 90만 발화. 단서는 발화 길이, 말 겹침, 멈춘 뒤 다시 말한 쪽이 누구인지다. 통화가 끝난 뒤 돌리므로 다음 대화까지 볼 수 있다. 사람 정답지와 대조해 점검했다. | [공식] |
| 맞장구 라벨 실험 | ① 별도 클래스 ② "답하기"에 포함 ③ "기다리기"에 포함, 셋을 비교했다. 라벨 정의가 실제 응답 성향을 바꿨다. | [공식] |
| 속도 | 모델 계산 중앙값 약 101ms, 전처리 포함 약 116ms, 95%가 170ms 안. RTX A6000, 오디오 길이 중앙값 6.9초. 서빙은 vLLM(오디오 배치 버그 수정 PR을 올렸다고 함). | [공식] |
| 구분 성능 | LiveKit **EoT-Bench 한국어**(멈춤 759개) AUC: 자사 후보 0.952 / 0.939, LiveKit v1-mini 0.919, SmartTurn v3.2 0.842, ultraVAD 0.803. "공개 모델 점수만으로 전화 환경 성능을 판단하기 어렵다"고 적었다. | [공식] |
| 대기 정책 | 중간 멈춤 오끊김을 **5% 이하**로 맞췄을 때 평균 대기 약 **0.58초**(모델 계산 시간 제외). | [공식] |
| 87% 수치의 원본 | 사내 카페 전화, 2026-08-24~09-07. 판단 요청 9,521건, 대조 가능 8,210건. 답하기 6,199(75.5%) / 기다리기 2,011(24.5%). 기다리기 중 1,750건(87.0%)이 1.5초 안에 말을 이었다. 글 스스로 "이어짐만으로 품질을 평가할 수 없고, 개선율이 아닌 운영 관측값"이라고 밝혔다. | [공식] |
| 다루지 않은 것 | barge-in, "어/음" 같은 한국어 머뭇거림 토큰 분석, 실패 사례 목록. 향후 과제는 소음 환경 안정화와 "주문을 생각하는 시간에는 기다리기". | [공식] |
| 참고한 것 | TEN Turn Detection, Pipecat Smart Turn, LiveKit EoT-Bench·v1-mini, ultraVAD. VAP·TurnGPT 같은 학술 논문은 글에 없다. | [공식] |

**비교 참고:** LiveKit Turn Detector v1(2026-06-17)은 자사 벤치에서 오끊김 5% 기준 평균 543ms, 10% 기준 295ms라고 밝혔다. 채널톡 0.58초와 비슷한 수준이다. 두 수치는 데이터 범위가 달라 직접 비교할 수 없다. [2차] [LiveKit 블로그](https://livekit.com/blog/solving-end-of-turn-detection)

## 3. 대화 엔진·지연·확인 설계 — 아웃바운드 엔진 2026-10-23

| 항목 | 내용 | 우리 주문에 적용 | 등급 |
|---|---|---|---|
| 노드 기반 | 흐름을 미리 정할 수 있으므로 **다음 대사는 미리 써 두고, LLM은 손님 답을 분기 중 하나로 분류**만 한다. 엔진이 다음 노드 대사를 실행한다. | 주문 상태 머신(인사→메뉴→옵션→수량→픽업→복창→확정)과 같은 구조. 고정 문장은 템플릿. | [공식] / [추론] |
| 전역 규칙 | "어디서 전화하셨어요?", "다시 걸어 주세요" 같은 공통 요청은 모든 노드에 분기를 반복하지 않는다. 현재 노드보다 **먼저 처리하는 전역 규칙(Global Interrupt)**으로 둔다. | "다시 말해 주세요", "메뉴 뭐 있어요?", "사장님 바꿔 주세요", "취소할게요"를 전역 규칙으로. | [공식] / [추론] |
| 수집·확인·정정 | 자유 답변에서 필요한 값을 추출한다. 하네스 안에서는 LLM이 후속 문장을 만들 수 있지만, **엔진이 필요한 값과 확인 여부를 관리**하고 완료 조건을 채워야 다음 단계로 간다. 주소처럼 중요한 값은 **읽어 주고 확인받고, 정정하면 고친 값으로 다시 확인**한다. | 메뉴·수량·옵션·픽업 시간·전화번호를 슬롯으로. 복창 후 "맞으세요?" 정정 시 다시 복창. | [공식] / [추론] |
| SVAD | 음성 활동이 아니라 **의미로 답변 완결을 판단**한다. 현재 질문 + STT 결과를 LLM에 넣는다. 완결이면 바로 적용, 미완결이면 조금 더 기다린 뒤 추가 발화가 없으면 보류한 결과를 적용한다. | **우리 TD 대체안의 직접 근거.** HCX에 "현재 질문 + STT 결과"를 주고 완결 여부를 받는다. | [공식] |
| 판단 무효화 | LLM 응답을 기다리는 중에 손님이 다시 말하면 미적용 판단을 버리고 합친 발화로 다시 판단한다. 늦게 온 취소 요청 결과는 **호출 ID와 발화 버전**으로 걸러 낸다. | 그대로 가져온다. 턴 ID·발화 버전 카운터를 서버 상태에 둔다. | [공식] |

## 우리 설계에 가져올 것(확정 아님)

1. **턴 판정 3단 구조.** 브라우저 VAD 멈춤(400~600ms) → 끝말 규칙 → HCX-DASH-002 3분류(끝남/이어짐/맞장구). "이어짐"이면 최대 1.5초 더 기다린다. 근거는 채널톡 TD·SVAD 글과 87% 수치다.
2. **판단 무효화 장치.** `turn_id`와 `utterance_version`을 두고, 늦게 온 HCX·TTS 결과는 버린다. barge-in 취소에도 같은 장치를 쓴다.
3. **LLM은 추출·분류만, 대사는 상태 머신 템플릿.** 공통 요청 5~6개는 전역 규칙으로 먼저 처리한다.
4. **복창·확인·정정 강제.** 확인 전에는 주문 확정 이벤트를 보내지 않는다. 정정하면 고친 값으로 다시 복창한다. 슬롯은 여러 턴에 걸쳐 누적한다(SpokenWOZ cross-turn).
5. **대기 UX.** 생각 중에는 타이핑 효과음(파일)을 튼다. 메뉴 검색 전에는 "확인해 볼게요" 한마디를 넣는다. 무응답 5~10초 뒤에는 계속할지 묻는다.
6. **통화 중 선택지 줄이기.** 통화에서는 주문 하나만 처리한다. 그 밖의 문의는 사장님 콜백 카드나 스마트 ARS 영역으로 넘긴다.
7. **평가 루프 축소판.** AI 손님 + 텍스트 러너 + HCX 심판(전사와 상태 로그 비교)으로 시나리오 10개 × 5회, 체크 all-pass. 음성 경로는 사람이 20통 정도 직접 확인한다. 지표는 태스크 완료율, 오끊김률, 말 끝 → 첫 소리 평균이다.
8. **확인할 것.** "NCP만 사용" 규정이 자체 호스팅 오픈 모델(Pipecat Smart Turn)을 허용하는지 확인한다. 허용되면 2차 판정으로 붙여 볼 수 있다.
