# 07. 메뉴판 사진 읽기 속도: 어디서 몇 초를 줄일 수 있나

> 조사일 2026-11-21 · 대상 코드 `src/agenthan/agent/menu_photo.py`, `src/agenthan/agent/food_photo.py`, `src/agenthan/tools/image_cutout.py`, `src/agenthan/core/llm.py`

- 지금 흐름: 사진 분류(HCX-005 비전 1회) → 메뉴 읽기(HCX-005 비전 1회, 긴 변 2240px) → 새 메뉴마다 `localize()`(HCX-005 텍스트 1회씩 순차) → 음식 사진 누끼(GrabCut 5회, 1024px). 사진 1장(메뉴 3~5개)에 6~8초가 걸렸다.
- 이미 진행 중인 것: (a) 분류와 읽기를 한 번의 비전 호출로 합치기, (b) `localize()` 동시 호출, (c) 이름·가격을 먼저 보여 주고 설명·사진은 나중에 채우기. 이 문서는 이 세 가지의 효과를 숫자로 확인하고, 그다음에 더 줄일 곳을 찾는다.
- 등급: **[공식]** NCP 공식 문서 / **[2차]** 서드파티 글·코드 / **[실측]** 2026-11-21 이 저장소 코드로 직접 잰 값 / **[추론]** 위를 조합한 우리 판단. 확인하지 못한 것은 **미확인**으로 적었다.

## 1. 실측 (2026-11-21)

### 1-1. 조건

- **메뉴판 시험 사진이 저장소에 없다.** `tests/`, `web/`, 상위 폴더까지 찾았지만 음식 사진 2장(`tests/data/food/cake.jpg`, `pelmeni.jpg`)뿐이었다. 그래서 **합성 메뉴판**을 만들었다. 3024×2268(폰 4:3), 짙은 칠판색 바탕, 키릴 4개(Пельмени 9,000 / Медовик 6,500 / Борщ 8,000 / Сырники 7,500) + 한자 1개(臭豆腐米粉 9,500), 오른쪽에 음식 사진 2장과 캡션, 1.5도 회전, 약한 흐림, JPEG 88.
- 한계: 글자가 크고(메뉴 이름 높이 약 70px/3024px) 배경이 단순하다. **작은 글씨·조명 반사·복잡한 배경의 실제 메뉴판에서 해상도를 낮췄을 때 정확도는 확인하지 못했다.** 데모 전에 실제 메뉴판 사진 2~3장으로 한 번 더 봐야 한다.
- 호출: 이 저장소의 `chat_v3`(네이티브 v3), 모델 HCX-005, temperature 0.1, 루트 `.env`의 테스트 키(60 QPM). 맥북(M3 Pro)에서 서울 리전 호출. 총 19회 호출. 스크립트는 로컬 scratch(커밋 안 함).
- 리사이즈는 `fit_for_vision`과 같은 방식(OpenCV INTER_AREA, JPEG 90).

### 1-2. 해상도별 메뉴 읽기 (`READ_PROMPT` 그대로)

| 긴 변 | 파일 크기 | 시간(2회) | promptTokens | 맞은 항목(이름+가격 정확) | 틀린 것 |
|---|---|---|---|---|---|
| 2240 (지금) | 236KB | 4.18초, 4.48초 | 1,753 | 3/5, 3/5 | Медовик→Медобин, Сырники→Сырник |
| 1536 | 136KB | 3.89초, 4.53초 | 1,753 | 4/5, 4/5 | Медовик→Медовник (+캡션 중복 1회) |
| 1024 | 77KB | 3.55초, 3.54초 | 1,753 | 4/5, 4/5 | Медовик→Медовник |
| 768 | — | 3.37초 | 1,633 | 4/5 | Медовик→Медовник |
| 512 | — | 3.23초 | 1,431 | 4/5 | Медовик→Медовник |

- **입력 토큰이 1024px부터 1,753으로 고정된다** [실측]. 768px에서 1,633, 512px에서 1,431로 줄어든다. 서버가 큰 사진을 일정 크기로 줄여서 같은 수의 이미지 토큰으로 만든다는 뜻이다. 그러니 2240px로 보내도 모델이 보는 정보량은 1024~1280px과 거의 같다 [추론].
  - 공식 문서에는 이미지 토큰 계산 방법이 없다(긴 변 2240px, 20MB, 비율 1:5~5:1만 적혀 있다) [공식]. 공개 모델 HyperCLOVAX-SEED-Vision-3B는 378×378 격자를 최대 9개(총 약 129만 화소)까지 쓰는 AnyRes 구조다 [공식 모델 카드]. HCX-005가 같은 구조인지는 미확인이지만, 1024px 근처에서 토큰이 멈추는 것과 맞는다 [추론].
- 시간 차이(2240 → 1024에서 0.6~0.9초)는 업로드 크기(Base64로 약 315KB → 103KB)와 서버 쪽 디코딩·축소에서 나온다 [추론]. 실제 폰 사진은 질감이 많아 같은 2240px라도 0.5~1MB가 넘으므로, 모바일 망에서는 차이가 더 클 수 있다 [추론].
- 정확도는 이 사진에서 해상도를 낮춰도 나빠지지 않았다. 오히려 2240에서 두 번 다 Медобин·Сырник으로 더 틀렸다. 표본이 작아 "낮추면 좋아진다"고까지 말할 수는 없다.
- Медовик 오독은 해상도와 상관없이 계속 난다(2026-11-08 기록과 같은 현상). Медовник은 가게 지식 글자 유사도 0.93이라 `match_known`이 잡지만, Медобин은 약 0.71이라 `FUZZY_MIN 0.8`을 못 넘는다 [추론, difflib 계산].
- **권장: `MAX_SIDE`를 1280으로.** 토큰이 멈추는 1024보다 조금 여유를 두고, 실제 메뉴판에서 작은 글씨가 문제면 1536으로 올린다.

### 1-3. 분류 호출, 합친 호출, 짧은 키

| 호출 | 시간 | promptTokens / completionTokens | 결과 |
|---|---|---|---|
| 분류만 (`CLASSIFY_PROMPT`, 2240) | **2.74초** | 1,691 / 3 | `menu_board` |
| 읽기만 (`READ_PROMPT`, 1536) | 3.89~4.53초 | 1,753 / 88~102 | 4/5 |
| **분류+읽기 합침, 짧은 형식** (1536) | **3.56초** | 1,753 / 80 | `t: menu_board` 맞음, 4/5 |

- 분류 호출은 출력이 3토큰인데도 2.7초가 걸린다. 비전 호출의 시간 대부분이 이미지 처리(입력 1,700토큰 prefill)이기 때문이다. 스트리밍 실측에서 첫 토큰까지 2.31초였다. **비전 호출 1회를 없애는 것이 가장 큰 절약이다.**
- 합친 프롬프트(실측에 쓴 것):
  `사진 종류를 t에 menu_board, food, other 중 하나로 적고, 메뉴판이면 보이는 메뉴를 m에 [이름, 가격] 배열로 적어라. ... 출력은 JSON 하나만: {"t":"menu_board","m":[["...",7500]]}`
  응답은 ```` ```json ```` 울타리로 감싸져 왔다. 지금 `_json_block`이 처리한다.
- 음식 사진이면 합친 호출이 `t: food`를 주고, 그다음 `read_food_photo`를 부른다. 음식 사진은 지금과 호출 수가 같고 메뉴판만 1회 줄어든다. 음식 사진도 줄이려면 합친 프롬프트에서 `food`일 때 이름·후보·box까지 같이 받으면 된다(미측정).
- 짧은 키(`[이름, 가격]` 배열)는 출력 88 → 80토큰으로 약 0.2초만 줄었다. 메뉴 이름(키릴·한자)이 토큰 대부분이라 키 이름을 줄여도 효과가 작다 [실측]. 출력 속도는 약 47토큰/초(88토큰을 1.89초에)였다.

### 1-4. 스트리밍 (1536, `READ_PROMPT`)

| 시점 | 시간 |
|---|---|
| 첫 토큰 | 2.31초 |
| 항목(`{...}`)이 닫힌 시점 | 2.60 / 3.00 / 3.35 / 3.71 / 4.16초 (+ 캡션 중복 4.17초) |
| 끝(`result` 이벤트) | 4.20초 |

- v3 스트리밍은 `Accept: text/event-stream` 헤더만 더하면 된다. 이벤트는 `token`(부분 `message.content`)과 마지막 `result`(전체 내용, usage)다 [공식, 실측]. 오류는 `ErrorEvent`, 그 밖에 `SignalEvent`가 있다 [공식].
- 붙이는 법 [추론]: `chat_v3` 옆에 스트리밍 함수를 하나 두고, 중괄호 깊이로 항목이 닫힐 때마다 그 조각을 `json.loads`한다. 닫힌 항목은 바로 화면(form.patch)에 올리고 `localize()`를 스레드풀에 넣는다. 끝에는 `result`의 전체 내용으로 한 번 더 파싱해서 맞춘다.
- 주의: 지금 `chat_v3`의 재시도(429·5xx 두 번)는 스트리밍 중간에는 쓸 수 없다. 스트림이 끊기면 스트리밍 없이 한 번 다시 부르는 쪽이 단순하다. 01 문서의 "스트리밍 + 도구 호출 400"은 도구 호출 이야기라 여기(이미지, 도구 없음)와는 관계없다. 이번 실측에서 이미지 + 스트리밍은 문제없었다.

### 1-5. `localize()` 순차 vs 동시

| 방식 | 시간 | 결과 |
|---|---|---|
| 순차 2개 | 2.35초 (1개 약 1.2초) | 펠메니, 메도빅 |
| 동시 5개 (스레드 5) | **1.57초** | 펠메니, 메도빅, 보르시, 쉬르니키, 취두부 쌀국수 |

- 순차 5개면 약 5.9초다. 동시 5개는 가장 느린 호출 하나만큼만 걸린다.
- 속도와 별개로 본 것: Сырники 설명이 "러시아 전통 감자 만두"로 나왔다(실제는 코티지치즈 팬케이크). 臭豆腐米粉은 설명이 비었다. `generated` 표시로 사장님 확인을 받는 지금 규칙을 유지한다.

### 1-6. 호출 한도

| 키 | HCX-005 한도 | 사진 1장이 쓰는 TPM(지금) | 사진 1장(바꾼 뒤) | 분당 처리 가능한 사진 |
|---|---|---|---|---|
| 테스트 키 | 60 QPM / 60k TPM | 분류 2.3k + 읽기 2.8k + 설명 5×약 0.45k ≈ 7.3k | 읽기(maxTokens 600) 2.35k + 설명 2.25k ≈ 4.6k | 지금 약 8장 → 약 13장 |
| 서비스 앱 키 | 300 QPM / 180k TPM | 〃 | 〃 | 약 39장 |

- TPM은 "입력 토큰 + `maxTokens`"로 센다 [공식]. 읽기에 `maxTokens 1024`를 걸면 출력이 90토큰이어도 1,024를 예약한다. 메뉴 30개(MAX_ITEMS)라도 출력은 약 550토큰이라 600이면 충분하다 [추론].
- 동시 5개는 QPM에 문제없다. 한 사람이 데모하는 동안에는 한도에 걸릴 일이 거의 없고, 팀이 테스트 키를 같이 쓰며 평가를 돌리는 시간과 겹칠 때만 429가 날 수 있다. `chat_v3`가 429를 두 번까지 재시도한다.
- `api_key()`는 `CLOVASTUDIO_SERVICE_API_KEY`가 있으면 HCX-005를 서비스 키로 부른다. `deploy/phone/.env`에는 서비스 키가 있고 루트 `.env`에는 없다. **데모 서버 환경에 서비스 키가 들어가 있는지 확인한다.** 서비스 키가 응답 속도 자체를 빠르게 한다는 문서는 없다(미확인). 한도만 넓어진다.

## 2. CLOVA OCR → HCX 텍스트 정리는 빠를까

| 항목 | 내용 | 근거 |
|---|---|---|
| 언어 | `lang`은 **ko, ja, zh-TW**만. 영어는 표시 없이 기본 지원. 키릴·간체·베트남어·태국어 언급 없음. 2024~2026 릴리스 노트에도 언어 추가 없음 | [OCR General API](https://api.ncloud-docs.com/docs/ai-application-service-ocr-ocr), [도메인](https://guide.ncloud-docs.com/docs/clovaocr-domain), [릴리스 노트](https://api.ncloud-docs.com/docs/ai-application-service-ocr-releasenote) [공식] |
| 출력 | `inferText`, `inferConfidence`, `boundingPoly.vertices`(V2만), `lineBreak`. 표 추출(`enableTableDetection`)은 도메인에서 켜야 함 | [공식] |
| 입력 | jpg·png·pdf·tif, 50MB, 1회 1장 | [공식] |
| 속도 | **공식 수치 없음**. 권장 최대 1 TPS(서비스 계정당) | [사용 준비](https://guide.ncloud-docs.com/docs/clovaocr-spec) [공식]. "써 봤는데 느리다"는 2023년 개인 후기가 검색 요약에 보였지만 원문은 확인하지 못함 [2차, 미확인] |
| 가격 | General 월 100건 무료. 초과 단가는 가격 데이터에 3원·22원 두 항목, 표 추출 건당 25원. API Gateway 요금 별도 | 팀 선행 조사 16b [공식 가격 데이터, 재확인 못 함] |
| 준비 | 콘솔에서 도메인 생성 + API Gateway 연동 + Secret 발급. 지금 `.env`에 OCR 키 없음 | [공식], 로컬 확인 |

**판단: 데모에는 쓰지 않는다** [추론].
1. 데모 가게는 러시아·몽골 사장님 메뉴판(키릴)이다. OCR이 지원하지 않는 문자다.
2. 빨라질 근거가 없다. OCR이 1초에 끝난다고 해도, 그 텍스트를 메뉴 JSON으로 정리하는 HCX 텍스트 호출이 같은 약 90토큰을 출력해야 한다(약 1.9초 + 첫 토큰). `localize()` 실측(약 40토큰에 1.2초)으로 보면 정리 호출만 2초 이상이다. 합치면 약 3~4초로, 1024~1280px 비전 1회(3.4~3.6초)와 비슷하다.
3. 호출이 두 군데(OCR, HCX)로 늘고 콘솔 설정이 남아 있다. 이틀 남은 데모에 넣기에는 위험이 크다.
- 나중에 쓸 곳: 한국어·일본어·대만어 메뉴판에서 **가격 숫자 검증**(OCR 숫자와 비전 가격 비교)과 **글자 박스**. 글자 박스가 있으면 "글자가 없는 큰 영역 = 음식 사진"으로 사진 위치를 잡고, 사진 바로 아래 캡션 박스로 어느 메뉴 사진인지 이어 줄 수 있다. 다만 3장의 OpenCV 방법이 키릴 메뉴판에서도 같은 일을 15ms에 하므로, OCR 박스만을 위해 붙일 이유는 약하다.
- 참고: Papago 이미지 번역도 메뉴판을 다루지만 메뉴 이름·가격을 구조화해 주지 않아 이 흐름과 맞지 않는다 [추론].

## 3. 메뉴판 안의 음식 사진 찾기와 흰 배경 누끼

### 3-1. 사진 영역 찾기: 세 가지 비교 (합성 메뉴판 1장)

정답(회전 전 위치, 0~1 좌표): 펠메니 사진 [0.63, 0.17, 0.95, 0.41], 케이크 사진 [0.63, 0.57, 0.95, 0.89].

| 방법 | 시간 | 결과 | 이름 연결 | 판단 |
|---|---|---|---|---|
| HCX-005에 사진별 bbox 요청(별도 호출, 1536) | 3.51초 | 펠메니 [0.59, 0.13, 0.94, 0.45] IoU 약 0.65 / 케이크 [0.58, 0.66, 0.95, 0.97] IoU 약 0.51 | 케이크를 **Сырник으로 잘못 붙임**(캡션은 Медовик) | 위치는 대충 맞고 이름은 믿기 어렵다 [실측] |
| OpenCV 윤곽(채도·에지 → 닫힘 연산 → 큰 사각형만), 1024px | **0.015초** | 펠메니 [0.62, 0.15, 0.95, 0.44] IoU 약 0.80 / 케이크 [0.63, 0.56, 0.96, 0.93] IoU 약 0.84 | 없음 | 단순한 배경에서는 정확하다. 실제 메뉴판(포스터, 컬러 글씨, 무늬 배경)에서는 오탐이 날 수 있다 [실측·추론] |
| GrabCut으로 사진 전체에서 찾기 | — | 사진 한 장 안의 "전경 하나"를 찾는 도구라 메뉴판에서 여러 사진을 찾는 데는 맞지 않음 | — | 영역 찾기에는 쓰지 않는다 [추론] |

- 이름 연결 방법(나중) [추론]: 합친 읽기 호출의 출력에 `"p": [[이름, [x0,y0,x1,y1]], ...]`를 더해 HCX에게 대략 위치와 이름을 받는다(출력 약 30토큰, 0.7초 정도 추가, 별도 호출 없음). 그 박스를 OpenCV 윤곽 박스 중 가장 많이 겹치는 것에 맞춰 위치만 바로잡는다. 이름이 틀릴 수 있으니 사장님 화면에서 "이 사진이 어느 메뉴인가요?"로 확인받는다.
- 데모에서 메뉴판 속 사진 오려 붙이기가 꼭 필요하지 않다면, **이번 데모에는 넣지 않는다.** 음식 사진은 지금처럼 따로 올린 음식 사진(`draft_from_food`)으로 처리한다.

### 3-2. GrabCut 비용 (음식 사진 1장, `cutout_on_white` 전체, 중앙값 3회)

| 처리 크기(`_MAX_SIDE`) | 반복 5회 | 반복 2회 |
|---|---|---|
| 1024 (지금, 펠메니 원본 960×540이라 실제 960) | **2.37초** | 1.62초 |
| 768 | 1.12초 | 0.79초 |
| 512 | 0.52초 | **0.36초** |

- M3 Pro 단일 스레드 기준이다 [실측]. NCP 서버의 일반 vCPU는 이보다 느릴 수 있어 지금 설정이면 서버에서 3초 이상일 수 있다 [추론]. 4032×3024 폰 사진은 1024×768로 줄어 960×540보다 화소가 1.5배라 더 걸린다 [추론].
- 512px·2회 결과를 1024px·5회와 나란히 놓고 눈으로 비교했다(펠메니, 케이크). 테두리와 접시 경계가 거의 같았다 [실측, 2장]. 마스크는 원본 크기로 키운 뒤 5×5 가우시안으로 흐리므로 512 마스크의 계단 현상이 잘 보이지 않는다.
- **권장: `_MAX_SIDE` 512, 반복 2회.** 사진 1장당 약 2초를 줄인다. 이 작업은 (c)대로 이름·가격을 보여 준 뒤 뒤에서 돌리면 체감 시간에서 빠진다. OpenCV 함수는 실행 중 GIL을 풀기 때문에 사진 여러 장은 스레드풀로 동시에 돌릴 수 있다 [추론].
- 외부 API 없이 더 빠른 다른 방법 [추론]:
  - 흰 접시·단색 배경이면 색 거리 임계값 + 가장 큰 덩어리만 남기기(수 ms). 배경이 복잡하면 실패하니 GrabCut의 대체가 아니라 앞단 빠른 경로로만 쓴다.
  - `cv2.saliency`, `cv2.ximgproc`는 지금 설치된 OpenCV 5.0.0에 없다(opencv-contrib 필요, 로컬 확인).
  - rembg(U²-Net) 같은 학습 모델은 빠르고 품질도 좋지만 NAVER Cloud 모델만 쓴다는 PRD 규칙에 걸린다. 쓰지 않는다.

### 나중

- 실제 메뉴판 사진 10장 정도로 해상도(1024/1280/1536) × 정확도 표를 다시 만든다. 이번 수치는 합성 1장 기준이다.
- 메뉴판 속 음식 사진 오려 붙이기: OpenCV 윤곽 박스 + HCX가 준 이름·대략 위치로 연결, 사장님 확인.
- 설명 만들기를 한 번에 묶기: HCX-007 구조화 출력으로 `{원어 이름: {name_ko, description_ko}}`를 받으면 순서가 섞여도 이름으로 맞출 수 있다(코드 주석의 "여러 개를 한 번에 보내면 순서가 뒤섞였다" 문제 회피). 호출 수가 줄어 TPM에 유리하지만 동시 호출보다 빠를지는 미측정.
- Медобин처럼 유사도 0.8 아래로 틀리는 키릴 오독: 가게 지식 후보 상위 3개를 사장님께 보여 주는 쪽이 빠르다(속도 문제는 아님).
- CLOVA OCR: 한국어·일본어·대만어 메뉴판에서 가격 교차 검증이 필요해질 때만.
